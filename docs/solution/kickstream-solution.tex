\section{Solution overview and scope}
% area:solution-overview

Kickstream is live-streaming software for football.
A host creates a broadcast, composes scenes in the studio, and goes live to
YouTube, X, Facebook and Twitch at once.
The picture on the program is a match event stream turned into live intelligence,
AI narratives and recaps.
Seven analyst agents, working in three teams, read the match as it happens.
A unified analytics dashboard joins the match, the agents, the audience and the
broadcasts on one page.
Auto live runs a channel by itself with a spoken commentator in twenty languages.
Agents then cut the recording's best moments into vertical reels.

The match is synthetic by default: a seeded simulator plays Northbridge FC
against Harbour City, two fictional clubs, so every insight can be produced and
replayed without licensed data.
This document describes the software in this repository: \texttt{apps/web},
\texttt{services/pipeline}, and the resources \texttt{deploy/terraform} creates.
It is not a store listing.

\subsection{What changed in this edition}

\begin{itemize}
  \item \textbf{Teams of analyst agents.} The seven match agents now work as the
    Match Reading, Forecast and Story teams. \texttt{/match} is called Analyst teams.
  \item \textbf{Unified analytics.} \texttt{/dashboard} shows the score, odds,
    expected goals, momentum, team stats, each team's and agent's work, the best
    players, the audience, the broadcasts and auto live, live.
  \item \textbf{Agent tools.} Each agent takes custom instructions, up to three
    connectors of the operator's own, and a chat.
  \item \textbf{Auto live in twenty languages}, each with a matching Azure neural voice.
  \item \textbf{Studio.} One commentary for the program, nine league-style background
    plates, element delete, a large solo camera frame, and a goal celebration.
  \item \textbf{Operations.} Deploy from GitHub with OIDC, match logs in Cosmos DB,
    and narration through a Microsoft Foundry project.
\end{itemize}

\section{Architecture and data flow}
% area:architecture-and-data-flow

Kickstream runs as one program.
Locally that is FastAPI on port 8000 and the Vite app on port 5173.
On Azure the template puts the server, which also serves the built web app, in a
single Container App.
Matches, the studio, and live streams are held in that process's memory, so the
app is pinned to one replica (\texttt{min\_replicas = 1}, \texttt{max\_replicas = 1}).

\subsection{Pipeline}

A match moves through five stages. The seven match agents publish findings onto
the same stream the browser reads. Stages talk only through the event bus and the
contracts in \texttt{packages/contracts}, and never import one another.

The gateway fans the match out with Server-Sent Events and WebSockets.
A late joiner is replayed the newest pitch scene and the newest player report, not the whole history.
WebSockets are accepted only from the host the pipeline was reached at.
Behind a proxy that rewrites \texttt{Host}, public names go in \texttt{KICKSTREAM\_ALLOWED\_HOSTS}.
On the Container App, \texttt{KICKSTREAM\_PUBLIC\_HOSTS} is the app's own address.

The seven match agents compute; one writes.
They are declared the way a Copilot Studio agent is: instructions, triggers,
tools, outputs and the agents they are connected to.

Narration, when a model is configured, is four Microsoft Agent Framework agents
sharing one Foundry client:
a Commentator and a Tactical Analyst on each key moment, a Recap Writer at
half-time and full-time, and a Localizer into Spanish and Hindi.
Each item is written once per mode and language and sent to every viewer on that
variant, so model cost does not grow with the audience.
Output is cached. If the model fails, that item falls back to a template and is marked scripted.
Only the Explainability Agent, among the seven match agents, writes prose.
That prose is English, at most 20 explanations a match.
Agent chat and Ask Copilot word their answers from the same recorded facts, plus
the agent's connectors when it has any.

\subsection{Where state lives}

\begin{itemize}
  \item \textbf{Playback, studio, encode.} Process memory locally, and the same inside the one replica.
  \item \textbf{Broadcasts, studio document, uploads, cache, fans, auto live, agent switches and instructions, connectors, keys, recordings, reels.} Directory \texttt{.data/} locally. Azure Files share \texttt{data}, mounted at \texttt{/data}.
  \item \textbf{Match log.} Memory unless Cosmos is configured. On Azure: database \texttt{kickstream}, container \texttt{match\_log}, partition \texttt{/match\_id}. Writes are queued and sent in the background, and a match not in memory is read back, so a restart keeps every replay.
  \item \textbf{Guest calls.} Communication Services, or \texttt{KICKSTREAM\_ROOMS=fake}. The deploy creates the Communication Services resource.
  \item \textbf{Model.} A Foundry project, or an OpenAI-compatible endpoint, otherwise templates. Terraform does not create Foundry.
\end{itemize}

Going live opens \texttt{/studio?output} (1920 by 1080) in a hidden Chromium browser.
ffmpeg encodes that picture once and copies it to every destination.
Microsoft Edge is used when it is present.
Auto live captures \texttt{/live?output} the same way.

\subsection{How it grows}

\texttt{docs/architecture/scalable.html} draws the shape to grow into: one match
owner, one encode, and viewers that scale apart.
A viewer gateway would scale with viewers, a studio API with hosts, a match worker
would hold one lease per match, and an encode worker one ffmpeg per live show.
That is a design note. It is not what \texttt{deploy/terraform} creates today.

\section{Functional capabilities}
% area:functional-capabilities

The path is Home, then a broadcast, then the studio.
Scenes are one library shared by every broadcast.

\subsection{Studio and the program}

The top bar names the broadcast, the output state (Off air, Connecting, or LIVE
with elapsed time), the scene on air, Edit layout, Ask Copilot, and the single
Go live / End broadcast control.
Tools, one at a time: Match, Banners, Comments, Guests, Replays, Timer, Stream, Settings.
Templates: Starting soon, Live match, Analyst desk, Break, Full-time, Interview,
Match intelligence, Fan zone, and 3D pitch.
The program carries one commentary, Fan or Analyst, for the whole studio.
Banners fire for goals and red cards, and a goal plays a short celebration on the program.
Replays animate the 20 seconds before a key moment.
Widgets cover score, charts, prediction, why it matters, 3D pitch, player card,
comments, poll, superchats, and spotlight.
Edit layout snaps, layers and deletes elements, and a scene can take one of nine
original background plates (Night, Claret night, Sun gold, Red and black, Blue
night, Navy gold, European night, Super League, Matchday pitch).
These are broadcast looks, not a club's or a league's crest.
The host can show a local camera without Azure; alone on the program it fills a
large frame. The hidden browser receives the camera and microphone only, never the screen.

\subsection{Destinations, broadcasts, reels, guests}

The Stream tool sends the program to YouTube, X, Facebook and Twitch.
Record to file writes an MP4 and needs no key.
Each destination shows connecting, live, retrying, or failed.
One failure does not stop the others.
The only sound is the guest call. With nobody unmuted, the stream is silent.

\DemoShot{figures/broadcast.png}{A finished broadcast: time on air, destinations reached, the score, key moments with their commentary, recordings, and each session's destinations.}

End broadcast keeps sessions, recordings, time on air, destinations, the score,
and key moments.
Generate reels cuts up to four 15-second vertical clips (1080 by 1920).
Each clip starts 8 seconds before its moment.
A Highlight Editor and a Social Copywriter run when a model is set; they do not
choose the edit points.
A reel can be edited in Clipchamp and the export added back beside the original.

Guest roles are Speaker, Co-host, and Member.
Speaker and Co-host can be placed on stage; a Member cannot.
A Co-host can go live, end or delete the broadcast, and make or revoke invites.
Up to four people are on stage.
Calls use Azure Communication Services Rooms.

Each agent can be switched off; the agents that listen to it then have less to work on.
For the studio's users, each agent also has:
\begin{itemize}
  \item \textbf{Custom instructions}, up to 2,000 characters. A model follows them,
    after its own rules, when it writes as that agent. What the agent computes does not change.
  \item \textbf{Connectors}, up to three per agent. When the agent is asked a question,
    Kickstream posts the question as JSON to each connector that is on, waits up to
    10 seconds, and cites the answer as a Connector source. Answers are given to the
    model as facts, never as instructions. At most 120 connector calls a match.
  \item \textbf{Chat}, answered from that agent's part of the match and its connectors.
    Anyone who can open \texttt{/match} can chat.
\end{itemize}

The chart counts calls the product allows in one match, not a measured audience.

\subsection{Unified analytics}

\DemoShot{figures/dashboard.png}{Unified analytics at 28 minutes: score, win chance, expected goals, analyst agents at work, highlights found, fan comments, time on air and auto live, above the win probability, expected goals and momentum, and team stats.}

\texttt{/dashboard} is one live page built from the streams the server already sends:
the score and odds, expected goals and momentum, team stats and tactics, work by
team and every agent's runs, highlights by kind, the best-rated players, the
audience's mood, platforms and topics, output and recent broadcasts, and auto live.
It is a studio page, behind sign-in on a public deployment.

\subsection{Ask Copilot, fans, auto live}

Ask Copilot answers from the live match and from the newest 50 finished matches
in \texttt{.data/matches.json}.
Cards never come from the model.
Web search is off until enabled: Wikipedia, or Tavily with \texttt{KICKSTREAM\_TAVILY\_API\_KEY}.
Typing \texttt{@} sends the question to one agent.
The same read-only answers are MCP tools at \texttt{POST /mcp}.

The fan zone starts on a demo feed.
X is optional.
Other platforms post to \texttt{POST /api/fans/ingest}.
Kickstream shows superchats and takes no payment.

\DemoShot{figures/live.png}{Auto live on: the Player Tracking Agent screen with a spoken line on screen, the 22 screens in the rotation, and the commentary language and voice.}

Auto live (\texttt{/live}) cycles 22 scenes, including one per match agent and one
of all seven at work, on a random gap the operator sets (5 to 10 minutes by default).
An AI commentator introduces each scene and speaks again as often as set.
Commentary speaks English, Spanish, Hindi, Portuguese, French, German, Italian,
Dutch, Polish, Turkish, Arabic, Russian, Chinese, Japanese, Korean, Indonesian,
Bengali, Tamil, Urdu or Marathi, each with matching Azure neural voices.
Screen labels exist in English, Spanish and Hindi.
Stream 24/7 publishes \texttt{/live?output} and restarts it if it drops.
It waits while the studio is on air.

\section{Security, privacy, and identity}
% area:security-privacy-identity

On a developer machine the application has no sign-in of its own.
Anyone who can reach the pipeline can stream to the configured channels, so the
API stays on that machine.
Stream keys live in \texttt{.data/output-keys.json} and are never sent back to a page.
A guest tunnel must be listed in \texttt{KICKSTREAM\_PUBLIC\_HOSTS} first.
If that list is empty, the gate is off and the tunnel would open the whole studio.

On Azure, Container Apps authentication signs studio users in with Microsoft Entra ID.
The application registration is named ``Kickstream studio'' plus the resource name.
\texttt{sign\_in\_audience} is \texttt{AzureADMyOrg}.
The only Graph permission is \texttt{User.Read}.
App-role assignment is required.
The deployer and every object id in \texttt{studio\_users} receive default access.
The app reads \texttt{KICKSTREAM\_SIGNED\_IN\_HEADER}, set to \texttt{x-ms-client-principal-id}.
When \texttt{public\_view} is true, anonymous clients reach the app and the app
keeps \texttt{/live} and \texttt{/match} read-only, sending studio pages, the
dashboard included, to \texttt{/.auth/login/aad}.
When it is false, anonymous clients are redirected to login.
\texttt{/guest/*}, \texttt{/api/guest/*}, and \texttt{/assets/*} stay open either way.

Only the studio's users can change an agent's instructions and connectors.
A connector key is sent in the header the operator names, or as a bearer token,
and is kept in the owner-only \texttt{.data/agent-secrets.json}, never shown again.
Connector addresses are readable by anyone who can read \texttt{/api/agents}, so a
key belongs in the key field, never in the address.
Redirects are not followed.
Connector answers reach the model as facts, never as instructions.

Cosmos DB has \texttt{local\_authentication\_enabled = false}.
The Container App's system-assigned identity holds Cosmos DB Built-in Data Contributor
on that account only.
Foundry is not created by Terraform.
If \texttt{foundry\_resource\_id} is set, the same identity receives Azure AI User
on that existing resource, and signs in to Foundry with Entra ID rather than a key.

Deploying from GitHub signs in through OIDC with no secret. The Entra app GitHub
Actions uses is trusted only for this repository's \texttt{production} environment.
It is an Owner of the subscription and holds two Microsoft Graph permissions,
\texttt{Application.ReadWrite.OwnedBy} and \texttt{AppRoleAssignment.ReadWrite.All},
so Terraform can register the studio's sign-in.
Terraform state sits in a private storage account used with Entra ID.

Container App secrets are the registry admin password, the Communication Services
connection string, the Entra client secret, the Speech key, and, only when
provided, the API-Football key and the LLM key.
The file share is Standard LRS with TLS 1.2 minimum, mounted with the storage
account access key.
The registry is Basic with the admin user enabled.

Fan text is truncated and shown as plain text.
MCP on a deployment sits behind the studio sign-in and only reads.
A co-host can end or delete the broadcast and can go live.
Synthetic clubs are fictional.
Favourite-club preferences stay in the browser.

\section{Deployment and operations}
% area:deployment-and-operations

\texttt{deploy/deploy.ps1} and \texttt{deploy/deploy.sh} require the Azure CLI
and Terraform 1.9 or newer.
They set \texttt{ARM\_SUBSCRIPTION\_ID} from \texttt{az account show}, apply the
container registry first, build \texttt{kickstream:<tag>}, then apply the rest
with \texttt{image\_tag}.
Build uses \texttt{az acr build}, or local Docker with \texttt{-LocalBuild} or
\texttt{--local-build}.
\texttt{deploy/destroy.ps1} asks before deleting the stack and the app registration
unless \texttt{-Force} is passed.
\texttt{deploy/destroy.sh} is the shell counterpart.

\subsection{From GitHub}

\texttt{.github/workflows/} holds two workflows.
\textbf{CI} runs on every push and pull request: ruff, the pipeline tests, a check
that both generated contract files match the schema, the web typecheck, tests and
build, and \texttt{terraform validate}.
\textbf{Deploy} runs after CI passes on \texttt{main}, or from the Actions tab, does
what \texttt{deploy.sh} does, and waits until the new revision answers.
It stays off until \texttt{deploy/github-setup.ps1} (or \texttt{.sh}) has created the
OIDC app, the state storage account, and the repository variables
\texttt{AZURE\_CLIENT\_ID}, \texttt{AZURE\_TENANT\_ID}, \texttt{AZURE\_SUBSCRIPTION\_ID},
\texttt{TFSTATE\_RESOURCE\_GROUP}, \texttt{TFSTATE\_STORAGE\_ACCOUNT} and \texttt{STUDIO\_USERS}.
\texttt{LLM\_API\_KEY} and \texttt{API\_FOOTBALL\_KEY} are repository secrets.

\section{Assumptions, constraints, and risks}
% area:assumptions-constraints-risks

\subsection{Assumptions}

The deploying operator can create the resource group, the Entra application, and
the role assignments; deploying from GitHub needs a subscription Owner and a
Global Administrator to grant the Graph permissions.
The image can run ffmpeg and Chromium.
Synthetic clubs are fictional, and a head-to-head is only matches this
installation has finished.
Viewers share narration; personalization is a gateway filter.
A model is optional. Templates are the supported path when no endpoint is set.
Connectors belong to the operator and are trusted to answer, not to instruct.

\subsection{Constraints}

StatsBomb Open Data is non-commercial and must not ship in a paid offer.
Kickstream does not implement Microsoft Marketplace SaaS fulfillment, an Entra
purchase landing page, or a live Partner Center offer.

One replica only.
Live feeds do not include ball positions.
API-Football's free plan is about 100 requests a day.
OpenLigaDB can arrive late, and its clock is estimated.
Explainability and Ask Copilot are English; auto live speaks twenty languages but
labels its screens in three.
Keyboard shortcuts are not implemented.
The stream has no bed and no crowd.
Reel in-points are fixed at 8 seconds before the moment, for 15 seconds.
The current templates pull the image with the registry admin user and mount
files with the storage account key.

\subsection{Risks}

A replica restart drops the in-memory match and the ffmpeg process.
The file share and the Cosmos log remain.

Auto live can restart a 24/7 stream from saved settings.
A studio encode does not resume itself.
The default public view lets anyone watch \texttt{/live} and \texttt{/match} read-only,
and chat with the agents there.
An empty public-host list plus a tunnel exposes studio controls.
A co-host invite is an operator credential.
The GitHub deploy identity is a subscription Owner; protect the \texttt{production}
environment and the \texttt{main} branch accordingly.
A connector address is visible through \texttt{/api/agents}; a key placed in it leaks.
S0 speech spends money per character, and the daily cap makes the captured voice
go quiet rather than switching the encode to the browser voice.
Record to file with Stream 24/7 fills the 10 GiB share.
Cosmos has a single region.
One failed destination does not stop the others, and nothing fails over to a
second region.

The safe commercial reading is: operate the synthetic match, or a feed you have
a right to use; keep StatsBomb off any paid offer; and do not describe a
Marketplace purchase flow as part of the product that ships today.
